## Findings

| # | Rule | Pri | Finding |
|---|------|-----|---------|
| 1 | R-03 | HIGH | Horizontal overflow at 390px, and the overflowing content is **clipped, not scrollable**. Three compounding causes. (a) `layouts/app.blade.php:147` uses `app-content flex-1` with no `min-w-0`, so the flex item cannot shrink below its min-content width. (b) `resources/css/app.css:122-123` sets `body { overflow-x: hidden }`, so the overflow is hidden rather than scrollable and the off-screen content is unreachable. (c) `.table-wrap` has **no CSS rule at all** in `app.css` although 31 views use it (`permissions/index.blade.php:43`, `users/index.blade.php:71`), so the intended table scroll container never existed. Measured at 390x844: `/permissions` docWidth 595 vs viewport 390, `/teachers` docWidth 731. Injecting `min-width:0` on `.app-content` drops `/teachers` to exactly 390 and clears the overflow, which confirms (a) as the primary trigger. Pre-existing and app-wide, not introduced by this feature, but the permission matrix is the widest table in the app (5 columns, 116 toggles) so it degrades worst. |
| 2 | R-27 | MEDIUM | No pending/loading state on any of the three save forms. "Simpan Matriks", "Simpan Perubahan" and "Simpan Pengecualian" all POST with nothing happening visually while in flight, so a double-click silently submits twice. The mechanism already exists: `form[data-busy]` in `resources/js/app.js:35-43` disables the button, adds `btn-loading`, and sets `aria-busy`. It is used exactly once in the entire app (`layouts/app.blade.php:138`); these three forms do not opt in. |
| 3 | R-06 | LOW | The "ditambahkan" / "dicabut" marker at `permissions/index.blade.php:77` is `text-[10px] uppercase tracking-wide`. At 10px uppercase with tracking it is the smallest text in the feature, and it carries the only signal that a grant was changed away from its role default. Raise to 11-12px, or drop the uppercase/tracking. This compounds finding 3 of audit 001, which already flagged the 11px uppercase `0.08em` treatment. |
| 4 | C-3, C-5 | LOW | The empty state at `users/index.blade.php:66-67` always reads "Ubah kata kunci atau filter peran yang dipakai." That is wrong when a tenant genuinely has zero users and no filter is active, which is reachable in practice: the Super Admin account exists before any school user does. Branch the copy on whether a filter is set. |
| 5 | R-25 | UNVERIFIED | Contrast could **not** be measured, so this audit does not claim a pass. The design tokens resolve to `oklab(...)` colors, which the browser canvas `fillStyle` will not normalize, so every computed value came back wrong (dark text on a light surface reported as 1.45:1, and a shared bogus `rgb(103,102,102)` background). The `contrast-check.py` helper ships with the `antislop-human` skill, which is not installed in this repo. Needs that skill, or a manual check of the tokens actually touched. |

## Fixed during implementation (recorded, not pending)

1. `->middleware('role:super_admin,admin_sekolah,permission:permissions.view')`
   is comma-split by the router, so `permission:permissions.view` was passed to
   `RoleMiddleware` as a **role name** and the permission middleware never ran.
   This affected `users.*` and `permissions.index` (introduced this session)
   and `permissions.update` (pre-existing). Fixed with array syntax
   (`->middleware(['role:...', 'permission:...'])`) and locked down by
   `test_permission_middleware_is_never_swallowed_into_role_parameters`.
   This was a live access-control failure, not a cosmetic one.
2. The sticky save bar covered the last rows of the matrix. Fixed with
   `pb-28` on the form; measured clearance is now 25 px with all 29 rows
   reachable.

## Resolutions

Owner approved findings **1** and **2** only. Findings 3, 4 and 5 stay open.

### Finding 1 - R-03 mobile overflow: RESOLVED

Three edits, no new dependency:

- `resources/views/layouts/app.blade.php:147` - added `min-w-0` to
  `app-content`. This was the primary trigger: a `flex-1` item defaults to
  `min-width: auto` and cannot shrink below its min-content width.
- `resources/css/app.css` - gave `.table-wrap` the rule it never had, next to
  the existing `.table` block:
  `overflow-x: auto; overscroll-behavior-x: contain; -webkit-overflow-scrolling: touch;`
- `resources/views/permissions/index.blade.php:44` - `min-w-[640px]` on the
  matrix table, so the widest table in the app scrolls instead of crushing four
  role columns into 390 px.

`body { overflow-x: hidden }` was deliberately **kept**. It is no longer the
thing hiding content, because the overflow is now contained and reachable, so
it acts only as a safety net. Removing it would let a future regression become
user-visible, which is a separate decision.

Evidence at 390x844, 18 pages (`/dashboard`, `/permissions`, `/users`,
`/users/create`, `/teachers`, `/students`, `/rombels`, `/academic-years`,
`/subjects`, `/schedules`, `/journals`, `/assignments`, `/assessments`, `/ews`,
`/audit-logs`, `/settings`, `/attendance`, `/attendance/scan`), all HTTP 200,
zero console errors, zero failed requests:

- `window.scrollX` after attempting a 600 px horizontal scroll is **0 on every
  page**, so nothing scrolls off-canvas any more.
- Every `.table-wrap` reports `scrollWidth > clientWidth` and can be scrolled to
  its end: `/audit-logs` 659 px of internal scroll, `/students` 464 px,
  `/permissions` 284 px, `/users` 270 px, `/teachers` 341 px.
- `clippedText: 0`. No `td`/`th` has text wider than its own cell, so nothing
  is truncated inside a scroll container.

Note on method: `documentElement.scrollWidth` still reports 620 on
`/permissions`, which looks like a failure but is not one. It counts the
`min-w-[640px]` table that is being clipped by its scroll container, and the
behavioural probe above shows that content is fully reachable. Trusting
`scrollWidth` alone would have produced a false FAIL here.

### Finding 2 - R-27 pending state: RESOLVED

Added `data-busy` to the four write forms: `permissions/index.blade.php:31`,
`users/create.blade.php:15`, `users/edit.blade.php:15` and
`users/edit.blade.php:28`. This opts them into the existing handler at
`resources/js/app.js:35-43`, which was already in the codebase but used once.

Measured on `Simpan Matriks`: before click
`{disabled: false, aria-busy: null, btn-loading: false}`, after click
`{disabled: true, aria-busy: "true", btn-loading: true}`. `aria-busy` is the
part that matters for a screen reader, since the button is now disabled while
the POST is in flight.

`npm run build` succeeds. Full suite green three consecutive times:
293 passed, 1074 assertions.

**Caveat worth recording:** the suite failed twice under load during this
session, once with 15 failures and once with 1, both while a dev server was
being hit by browser QA and a production build was running. A run that took
83 s against a usual 13 s is the tell. Three clean runs followed once the
machine was quiet. Nothing observed points at a real ordering bug, but the
suite has not been proven stable under concurrent load, and that is a weaker
claim than "green".
